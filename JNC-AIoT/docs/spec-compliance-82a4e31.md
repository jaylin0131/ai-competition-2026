## I1　主機斷線時產生工單出錯（會當掉）

- **位置**：`decide/engine.py` 第 64–76 行（情境 A 系統失效）
- **現象**：情境 A 在第 76 行 `return out` 提早結束，沒有執行第 168–169 行補上的「編號」欄位；接著 `decide/workorder.py` 第 27 行讀 `d["編號"]`，出現 `KeyError: '編號'`。
- **重現**：

  ```python
  from common.pipeline import PondPipeline
  PondPipeline.build().step("2026-08-11 14:00")   # 回放期間唯一的斷線小時
  ```

- **影響**：Streamlit 平台回放到這一小時會出錯；「系統失效 → Fallback」這條企業明列的規則在實際回放中跑不出來。
- **為什麼測試沒抓到**：`tests/test_pipeline.py` 的 `test_decide_nine_fields_and_modes` 只測 `decide()`，沒有接著跑 `work_orders()`。
- **建議修法**：情境 A 也走同一段補編號與排序的程式（不要提早 `return`，或把補編號抽成函式在 return 前呼叫），並新增測試：斷線狀態下 `work_orders(decide(...))` 不出錯，且 Fallback 決策有編號。

- **處理結果（d2f18fa）**：所有 return 都經過 `_finalize()` 補編號與排序；新增斷線時 `work_orders(decide(...))` 的測試。8/11 14:00 回放會產生 Fallback 決策＋感測主機檢查工單。


## I2　風險「中」卻自動執行

- **位置**：`decide/engine.py` 第 101–109 行（情境 C 預測性增氧）
- **現象**：`params.json` 的 `validated = true` 時，預測性增氧一律 `自動執行`，但當 DO ≥ 3.0 時風險欄標「中」。
- **實測**：回放期間「主增氧機未開且低溶氧機率 > α」共 23 小時，自動執行的決策中 19 筆風險「低」、**4 筆風險「中」**。抽樣全部回放時段也有同樣情形。
- **企業規格**：低風險且已驗證才可自動執行；高風險人工確認。
- **測試也把這個組合當成預期結果**：`test_decide_nine_fields_and_modes` 第一段斷言 DO 3.4、預測性增氧要「自動執行」，此時風險為「中」。
- **建議修法（二選一，週會決定）**：
  1. 風險「中」一律改人工確認，只有「低」才自動執行；或
  2. 預測性增氧的風險改標「低」，並在理由寫明「啟動增氧機方向安全，最壞情況只是多耗電」。

  不論選哪個，都要同步修改測試，並在 `decide/engine.py` 開頭的說明寫清楚「風險」與「執行模式」的對應規則。

- **處理結果（d2f18fa）**：採**方案 1**。理由：方案 2 是把「預測會低」也標成低風險，等於讓模型預測直接驅動設備；企業規格是「低風險且已驗證才自動」，而預測有誤報（每週約 0.7 次），由人確認比較符合安全控制原則，且回測假設人工確認都會核准，成效數字不變。`decide/engine.py` 的 `_d()` 統一把關：非「低」風險一律降為人工確認；DO 已低於門檻的增氧為「低」風險，已驗證時自動執行。新增測試：回放中所有自動執行的決策風險都是「低」。


## I3　沒有預測增氧機（設備）故障機率

- **位置**：`forecast/pond.py` 的 `forecast()`；`fail_prob` 來自 `probe_rul()`，只算水質探頭。
- **現況**：增氧機只有「已經發生」的診斷（`diagnose/pond.py` 的 `equipment_fault`：運轉中功率 < 650 W），沒有預測。
- **企業規格**：趨勢預測要輸出「設備故障機率」；問題 02 要預測「設備故障」。
- **建議做法**：用 CPM 功率在運轉時段的趨勢（下降斜率、低負載小時比例、功率因數變化）估計增氧機未來 24–48 小時出現低負載的機率；`forecast()` 另外輸出 `aerator_fail_prob`，決策引擎在機率高時產生預防性檢修工單。

- **處理結果（1c84986）**：`forecast/pond.py` 的 `aerator_health()` 用運轉功率 24 小時趨勢外推到 650 W，輸出 `aerator_fail_prob`（48 小時內）；≥ 0.5 時決策引擎排「增氧機預防性檢修」（人工確認）。資料中增氧機沒有真的故障，以合成功率衰退驗證：提前 35–38 小時預警，真實資料誤報 0（report 2.2）。


## I4　沒有輸出營運風險

- **現況**：有低溶氧機率 `p_low`、用電與電費，但沒有把它們轉成營運面的風險。
- **企業規格**：問題 02 要預測「營運風險」。
- **建議做法**：`forecast()` 或 `decide()` 加上營運風險估計，例如「預期損失 = 低溶氧機率 × 單位損失 + 危急機率 × 單位損失 + 增氧電費」，單位損失沿用回測的成本設定（低溶氧每小時 100 元、危急每小時 300 元），並在平台與三個問題的回答中顯示。

- **處理結果（1c84986）**：`ops_risk()` 輸出 6 小時預期損失與低／中／高，平台預測頁與三個問題都有顯示；單價集中在 `common/config.py`，回測成本函數共用。分級對照實際結果：期望低溶氧時數 0.1／2.3／5.7 h，實際 0.1／2.3／5.7 h（report 2.3）。斷線時為「高（無資料）」。


## I5　沒有 GI 指標

- **位置**：`state/pond.py`；平台「狀態辨識」分頁以設備健康度暫代。
- **現況**：企業流程圖寫「WQI／GI」，但沒有說明 GI 是什麼。
- **處理**：已列在 [decisions-pending.md](decisions-pending.md) Q2，等企業回覆後再實作；在那之前說明書要寫明「GI 定義待企業確認，暫以設備健康度呈現」。

## I6　環境資料沒進入預測與決策

- **位置**：`forecast/pond.py` 的 `features()`、`diagnose/pond.py` 的 `IForest.FEATURES`
- **現況**：OA4 氣象站（氣溫、濕度、氣壓、熱指數）只在診斷中用來偵測「氣象站凍結」，預測特徵只用水溫、pH、ORP、SC 與功率。
- **企業規格**：01 IoT 感測要涵蓋「水質、設備、環境」。
- **建議做法**：把氣溫、氣壓及其變化量加入 DO 預測特徵（氣壓下降、悶熱夜晚常伴隨低溶氧），重跑回測比較 MAE；氣象站被判定凍結時，該特徵改用缺值。注意 OA4 有約 5% 為 0、9/14 起凍結（events.md P18）。

- **處理結果（1c84986）**：氣溫與水溫差、氣壓 3／6 小時變化、濕度進入 DO 預測；氣象站凍結或 0 時當缺值（約 25% 的小時）。MAE 與不含環境相差 ±0.003 以內，預警 30→31 件、提前 4.9→5.2 小時，每週誤報 0.65→0.75（report 2.1）。平台狀態頁顯示環境值。


## I7　執行回饋沒有接回再學習

- **位置**：`app/streamlit_app.py` 的「執行回饋」分頁（`st.session_state.log`）、`scripts/run_backtest.py`
- **現況**：平台上核准、駁回、送 SCADA 執行的紀錄只存在瀏覽器工作階段，重新整理就消失；α、β 的再學習要另外手動執行回測。
- **企業規格**：05 執行回饋要「驗證結果再學習」。
- **建議做法**：執行紀錄寫入檔案（例如 `backtest/feedback.csv`）；平台加一個「依執行結果重新學習」按鈕，呼叫回測的再學習流程更新 `decide/params.json`，並顯示更新前後的 α、β 與驗證期成本。

## I8　平台不能注入故障

- **位置**：`app/streamlit_app.py` 側欄
- **現況**：`common/replay.py` 有 `inject_faults()`，但平台沒有使用；回放期間只有 8/11 14:00 一小時是斷線，決賽很難現場示範 Fallback 和「壞探頭被自動排除」。
- **建議做法**：側欄加「注入故障」選單（卡值、漂移、跳點、掉 0、斷線，以及要注入的探頭），注入後重新計算狀態、診斷與決策。需先完成 I1。

- **處理結果（bb1abe6）**：側欄「注入故障」可選卡值、漂移、跳點、掉到 0、主機斷線，以及探頭與已持續時數；`PondPipeline.with_fault()` 重算該段狀態、診斷與預測，畫面顯示示範模式提示。有測試。


## I9　只預測溶氧

- **現況**：`forecast/pond.py` 只有 DO 的 1–6 小時預測與超標時間。
- **建議做法**：至少加上 pH 的短期預測與超出 6.5–9.0 的時間；若時間不夠，說明書寫明「魚塭最關鍵的是溶氧，其他水質以狀態辨識與診斷處理」。

## I10　儲存與歷史基準的使用範圍

- **現況**：資料存在 `data/processed/*.csv` 與 `.cache/*.pkl`，沒有時序資料庫；`common/baseline.py` 的歷史基準只有 Isolation Forest 使用，狀態辨識與診斷用的是三探頭互比與固定門檻。
- **建議做法**：說明書說明「以檔案模擬企業既有的資料平台」即可；有餘力再讓診斷加入「偏離歷史同時段」的證據（例如「DO 比過去同時段中位數低 2.1σ」）。

## I11　決策沒有逐筆比較成本

- **現況**：決策引擎依規則由上而下選擇行動；「成本」只在回測挑 α、β 時用到。
- **企業規格**：04 決策引擎要考慮「目標、規則、風險、成本」。
- **建議做法**：每筆決策加上「預期成本／效益」欄（電費 vs 降低的低溶氧風險，可與 I4 共用計算），並在備用增氧機、節能停機等選項之間依預期成本排序。
